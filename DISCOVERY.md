# Discovery: Meta models for Crumbs — what to test, in what order

Status: discovery, 2026-10-27; updated 2026-10-28 with the first measured results (E0 corpus sample, E2 secondary arm). This document decides **what to test** before [BRAINSTORMING.md](BRAINSTORMING.md)'s direction becomes a PLAN.md. Product direction and use cases live in BRAINSTORMING.md; this file covers the Meta model catalog as it applies to Crumbs, the local-hardware question, and the experiments with pass/kill criteria. [PLAN.md](PLAN.md) and [IMPLEMENTATION.md](IMPLEMENTATION.md) are now the build documents; this file remains the model-story record.

Facts below are from Meta's own pages, fetched 2026-10-27 (sources in §7). Anything not verified there is marked **to test** — do not quote it as a capability until the experiment runs. Measured results are dated and name their worklog entry; catalog facts and measurements must not be conflated.

## Decision: local-only processing is the core (2026-10-27)

**The shipped system processes everything locally, with local models only.** All image classification, embedding, evidence extraction, visit reconstruction, and agentic retrieval run on the user's own hardware; no photo, location record, or derived image content is sent to a cloud model API. This is a product-defining claim — privacy is a headline feature, not a fallback mode — and it constrains every model choice below:

- **In the shipped pipeline:** local open models only — Muse Glimmer and DINOv3 today, with Perception Encoder, local SAM 3.1, and PLM as test candidates (§2.1) that may join or split roles based on E1/E3/E4 results — plus local non-model code (EXIF/metadata, geospatial index). The list may grow with local models; it may not gain a cloud model.
- **Not in the shipped pipeline:** Muse Spark / Wonder (API-only), Muse Spark Open *as hosted by a partner* (self-hosting it is impractical at 816B; partner hosting is cloud processing), the SAM 3.1 *API* (the open checkpoints are local and eligible — see §2.1), Muse Image (API-only). These may be used **during development only** — e.g. as a quality oracle on the consented demo subset to measure how far local models are from the cloud ceiling — and that use must be disclosed wherever results are quoted. A benchmark number produced by a cloud model is never presented as the product's output.
- **One explicit, optional exception:** voice input. Muse Voice Transcribe is API-only, so if voice recollection/search ships at all, it is off by default, clearly labeled as sending *audio* (never images or location history) to Meta's API, and the system must be fully usable without it. A local speech-to-text alternative is an E7 probe; if neither is acceptable, voice is cut. Wording rule: we may say “all image and location processing is local; optional voice transcription is the only cloud feature, and it is off by default” — we may not say “fully private / nothing leaves the device” while that exception is enabled.
- **Hardware reality:** the lead has RTX PRO 6000 (96 GB) cards available, plus a Strix Halo (AMD, unified memory) box. That removes the main feasibility risk: SGLang's verified-platform matrix lists Muse Glimmer **bf16 on a single RTX PRO 6000**, and vLLM needs ≈72 GB VRAM to serve bf16 — both fit one PRO 6000. CUDA (vLLM/SGLang/PyTorch) is therefore the primary local target; llama.cpp/ONNX cover portability, and Strix Halo becomes a secondary “does it also run on a consumer AMD box?” test rather than the gate for the whole local story.

## 1. The question

Crumbs needs five kinds of machine perception/reasoning:

1. **Triage and classification** of every photo (food / sightseeing / trip / personal, plus evidence types: dish, menu, receipt, sign, storefront, interior, lodging, landmark) — high volume, privacy-sensitive, ideally local.
2. **Visual similarity** — duplicate/burst detection, same dish or same storefront across different photos and visits.
3. **Evidence extraction** — reading signs, menus, receipts, and identifying dishes well enough to support place resolution (never to prove a place from food appearance alone).
4. **Cross-photo reconstruction** — reconciling a cluster of photos plus check-in/location records into a visit, with uncertainty stated.
5. **Agentic retrieval** — answering "near X, what did I enjoy / order before?" over the reconstructed history, and keeping a factual taste profile (what recurs, what the user confirmed liking).

Each Meta model below is evaluated only against these five jobs.

## 3. The local hardware question

Available hardware: **RTX PRO 6000 (96 GB) cards** (Blackwell, CUDA) and a **Strix Halo** box (AMD Ryzen AI Max class, Radeon integrated graphics, large unified memory). llama.cpp, vLLM, PyTorch, and ONNX are all in play. With that hardware the local stack is not a stretch goal; the questions are throughput, quality, and portability.

**Primary target — PRO 6000 / CUDA.** This is a vendor-verified Glimmer configuration, not a hope:

- SGLang's verified matrix lists Glimmer bf16 — the only multimodal checkpoint — on a single RTX PRO 6000 (96 GB); vLLM serving needs ≈72 GB VRAM (bf16 weights ≈60 GB plus KV cache/activations), which also fits one card. Multi-card tensor parallelism is essentially untested per the docs ("treat multi-GPU serving as untested"), so plan single-card serving per instance and parallelize across photos/instances instead.
- DINOv3 (PyTorch or ONNX) on the same card embeds a library at trivial cost relative to Glimmer generation; the embedding pass should never be the bottleneck.
- Serving choices to benchmark head-to-head in E2: vLLM vs. SGLang (both OpenAI-compatible endpoints, reasoning/tool-call parsers differ in flag names — `muse_glimmer` vs. `muse`; copy flags from the current recipe, they are version-sensitive).

**Secondary target — Strix Halo / AMD.** This answers “does it also run on a consumer box?” and widens the demo's credibility, but it no longer gates the product:

- No verified AMD/Strix Halo Glimmer deployment is published in the docs checked, and the published vLLM image is CUDA-pinned with no ROCm image. The promising path is llama.cpp (ROCm, then Vulkan) with the 17 GB GGUF Q4_K_M + `mmproj` vision projector; SGLang's GGUF path is text-only, so llama.cpp is the only documented multimodal route on AMD.
- **Measured 2026-10-28 (worklog 20261027T203902, GLM-05 first arm):** the HIP build of mainline llama.cpp on the lead's Strix Halo box (`zbook`, Radeon 8060S / gfx1151, 125 GB unified memory) runs the official Q4_K_M + mmproj + dflash GGUFs with vision end-to-end (HIP worked; the Vulkan fallback was not needed). Timings, single requests: image encode 1.9 s on a small synthetic card; full-resolution photos ≈ 4,150 prompt tokens at ~88 tok/s prefill (~47 s per photo before generation — image tokens dominate, so input downscaling is the tuning knob to measure next); generation 17–27 tok/s with `--spec-type draft-dflash` (draft acceptance 46–76% across three requests). Quality spot checks: exact transcription of a synthetic menu card; sensible scene descriptions of two real sampled photos. Verdict: the consumer story is real for background organizing (~a photo a minute at full resolution), not for interactive bulk import at full resolution; batch timing and the downscale/accuracy tradeoff remain open, and no bf16 comparison is possible on this box.
- DINOv3 small variants (21–89M parameters) run anywhere, including this iGPU or CPU, so classification/embedding on Strix Halo is low-risk even if Glimmer generation there is slow.
- Result framing: whatever E2 measures on Strix Halo is reported as the consumer-hardware story; the PRO 6000 numbers are the reference configuration. Do not quote PRO 6000 throughput as typical consumer performance. The PRO 6000 primary arm (E2, GLM-01/02) is still unmeasured — no access path to that box has been recorded yet.

**Architecture consequence.** The pipeline is local end-to-end (DINOv3 embeddings/heads → Glimmer extraction and reconstruction → local geospatial index and agent). If a local model cannot resolve a case, the product's answer is a targeted question to the user or an explicit unknown — never a silent cloud escalation. That behavior is itself a feature to demo: the system shows what it could not determine and asks exactly one useful question.

## 4. Experiments — what to test, in order

Run in order; each gates the next. All experiments use the same corpus (E0) so results are comparable. Record results in worklog entries with exact commands, model IDs/checkpoints, quantization, hardware, and counts — a result without its conditions is not a result.

### E0 — Golden corpus and reference labels (do first, blocks everything)

- **Build:** one real, messy trip collection plus local outings, with an overlapping structured location export (Foursquare or Google, per BRAINSTORMING's dataset check). Privacy-safe subset cleared for the public demo; the rest stays in ignored local directories.
- **Label by hand:** reference visits (place, time window), photo→visit assignment, photo category (food / sightseeing / trip / personal) and evidence type (dish, menu, receipt, sign, storefront, interior, lodging, landmark, none), and dish identity where known. Deliberately include unknowns, conflicting sources, and repeated visits to the same place.
- **Write the golden queries:** vague-memory questions ("the little place in Kyoto with the grilled fish"), geospatial questions ("near X, what did I enjoy?"), and reorder questions ("what was good last time at…?"), each with the expected visit/dish answer or an explicit "unknown."
- **Pass:** corpus and labels exist and cover at least one multi-day trip; without this, no other experiment's numbers mean anything.
- **Status 2026-10-28 (DAT-01 started, worklog 20261027T194921):** a 440-photo sample (40/month, Jan–Nov 2019, systematic over EXIF order) from the lead's local iCloud tree lives in the ignored `data/sample-2019/` with a manifest; EXIF coverage 413/440 DateTimeOriginal, 399/440 GPS. Still missing for E0 to pass: the paired structured location export (DAT-02) and the hand labels + golden queries (DAT-03/04).

### E1 — Embeddings and classification: DINOv3 vs. Perception Encoder (vs. Meta CLIP 2)

- **Question:** which local embedding stack does jobs 1–2 — and does zero-shot text classification beat a trained head?
- **Tests:** (a) near-duplicate/burst grouping by embedding similarity (both backbones); (b) same-dish and same-storefront matching across visits (DINOv3 patch-matching per the reference notebooks, plus global-embedding nearest neighbors from both); (c) taxonomy/evidence-type classification three ways: DINOv3 frozen features + lightweight linear/k-NN head trained on a small labeled slice of E0; PE-Core zero-shot from text prompts (no training); PE features + the same head. Meta CLIP 2 joins only if PE zero-shot disappoints, as the multilingual tiebreaker.
- **Metrics:** duplicate-group precision/recall; same-dish/storefront match accuracy on labeled pairs; classification accuracy vs. the hand labels with a confusion matrix (food-vs-personal is the expected hard boundary; misrouting a receipt away from extraction costs more than a sightseeing/personal swap). Also measure text-query retrieval ("receipt", "grilled fish") precision for the agent toolbox — PE's text alignment is its structural advantage here.
- **Pass/kill:** the winner owns triage and routing; expect a possible split (PE for text-aligned classification/retrieval, DINOv3 for visual matching) — adopt the split only if each half measurably wins its job, otherwise one stack. If all matching is weak, similarity falls back to metadata+time grouping and embeddings are demoted to dedup only.

### E2 — Muse Glimmer serving: PRO 6000 first, Strix Halo second

- **Question:** what does local Glimmer serving cost and deliver, per hardware target?
- **Primary (PRO 6000 / CUDA):** serve the bf16 checkpoint under vLLM and under SGLang; measure cold start, tokens/sec, seconds per photo for the fixed E3 extraction prompt (images included), peak VRAM, and stability/throughput over a 500-photo batch, including concurrent requests. Confirm tool calling and structured output through each server's parser flags. Use the published sampling settings (temperature 1.0, top_p 0.95, top_k 64; do not run greedy).
- **Secondary (Strix Halo / AMD):** llama.cpp (ROCm build, then Vulkan) with the Q4_K_M GGUF + `mmproj` vision projector; same measurements, reporting peak unified-memory use. Try the dynamic Q4 build if quality (measured in E3) is marginal.
- **Pass:** on the PRO 6000, the full E0 corpus extracts locally at a rate that makes “import a trip in minutes” true on one card. On Strix Halo, any working multimodal result with honest numbers is a pass for the portability story; failure there does not block the product, but must be recorded (it bounds who can self-host the full stack). **Kill/pivot:** if bf16 serving fails on the PRO 6000 — contrary to the vendor-verified matrix — fall back to quantized builds and re-measure quality in E3 before concluding anything; do not pivot to cloud, which the local-only decision forbids.
- **Status 2026-10-28:** secondary (Strix Halo) arm partially measured — see §3 for the numbers (worklog 20261027T203902). Remaining there: 500-photo batch timing, downscaled-input comparison, quantized-quality check in E3. Primary (PRO 6000) arm: not started; blocked on an access path to the box (IMPLEMENTATION GLM-01/02).

### E2b — Glimmer-DE: a System-1 decision layer on Glimmer (restricted-readout LoRA)

Reference pattern: **Shisa DE-2.1** (`shisa-ai/shisa-de-2.1`, Apache 2.0) — a general-purpose decision model built by LoRA-training a vision-language model (Gemma 4 26B A4B) so that classification is a *single forward read*: state + named question + up to 256 letter-coded options, answer read from the next-token distribution restricted to the option codes (`max_tokens=1`, no generated text), with per-read temperature calibration and an adaptive policy (read twice; think only when the top probability is low). Its card reports the pattern working on image classification with the vision encoder *untrained* (the readout training is on the language model), at 37 ms p50 per single read on one RTX PRO 6000 — on a 3.8B-active MoE. Glimmer is a 30B **dense** model, so the same read will be materially slower per forward; the question is whether it is fast and accurate enough to be Crumbs' routing layer, not whether the pattern works in principle.

- **What Glimmer-DE would decide in Crumbs:** the high-volume yes/no and multiple-choice calls that currently imply a slow generative answer — photo category (food/sightseeing/trip/personal), evidence type present? (receipt/menu/sign/dish/none), is this photo's evidence sufficient to identify a place?, same visit as the previous cluster?, route to extraction / ask the user / mark unknown. Calibrated probabilities are the point: they drive the routing thresholds and the abstention behavior the rest of the system depends on.
- **Feasibility checks first (cheap, blocking):** (1) option codes `A`–`Z`, `AA`… are single tokens in Glimmer's tokenizer (DE's contract requires it); (2) the serving stack (vLLM, then SGLang) can return the restricted next-token distribution — logprobs coverage for >20 options needs verifying, since top-k logprobs may not expose all option codes; (3) Axolotl/TRL LoRA training with loss on the answer token only (completion-only) reproduces DE's cross-entropy-over-option-codes objective — Glimmer's post-training docs confirm LoRA/QLoRA on the language projections with the vision tower frozen, including a vision QLoRA config, which matches DE's training shape.
- **Training data:** E0's labeled photos rendered as DE-style questions (one question per decision, option order shuffled/re-rendered per epoch, an explicit *none/unknown* option — DE-2.1's none-of-the-above and evidence-mention families are directly relevant to our abstention requirement). Multiple LoRA seeds, weight-averaged ("souped") if time permits — DE-2.1's eleven-run soup was its single largest measured gain; 3–5 runs is the realistic hackathon version.
- **Metrics:** decision accuracy vs. E0 labels, per question family; calibration (ECE before/after fitted temperature — refit on our data, DE's temperatures do not transfer); latency per read on the PRO 6000 (bf16) and per photo across the full question set, since the image prefill is paid per question under the one-request-per-question contract; batching behavior under vLLM continuous batching, which is where a dense 30B may still win on throughput even with slow single reads.
- **Comparators:** PE zero-shot and the DINOv3 head (E1) on the same questions — Glimmer-DE must beat or complement them to justify its cost — and Shisa DE-2.1 itself run locally as a pattern reference (its vision is the untrained base model's, so treat its photo accuracy as a floor demonstration, not a target).
- **Pass/kill/scope:** if a full question set per photo costs more than the generative pass it is meant to gate, Glimmer-DE shrinks to the few decisions embeddings cannot make (evidence sufficiency, abstention, visit-boundary calls) and PE/DINO keep bulk classification. If even that is too slow, distill: Glimmer-DE (or generative Glimmer) labels a large set, and a DE-style LoRA on PLM-3B becomes the shipped System-1 — record which, because the “one model, two speeds” story changes. Either way the System-2 escalation stays the same weights family: low calibrated probability → generative Glimmer reasoning (DE's think-when-unsure step, same model in our case).
- **Measured input (2026-10-28):** the Strix Halo run (§3) prices the per-question prefill problem concretely — at ~88 tok/s prefill and ~4,150 image tokens per full-res photo, re-prefilling per question is untenable on that hardware; Glimmer-DE reads there would need the image KV/prefix cached across questions (or downscaled inputs), while on the PRO 6000 the same design question is decided by the E2 primary-arm prefill rate, still unmeasured.

### E3 — Evidence extraction quality: local Glimmer, measured absolutely (cloud oracle optional)

- **Question:** on signs, menus, receipts, storefronts, and dishes (including Japanese text), is local Glimmer good enough to ship — measured against the hand labels, not against another model?
- **Tests:** fixed structured-output schema (visible text transcription, dish names, place-name candidates, confidence, "cannot determine") on the E0 evidence photos, for each serving configuration that passed E2 (PRO 6000 bf16; Strix Halo GGUF if it ran) **and for PLM-3B and PLM-8B** as smaller local comparators (document-like inputs are their published strength). Include the adversarial cases: dish-only photos where the correct place answer is "unknown."
- **Metrics:** transcription accuracy on readable text; dish-identification accuracy; place-candidate precision; **abstention correctness** (saying unknown when the evidence doesn't decide) — weighted as heavily as accuracy. Report per hardware/quantization so the Strix Halo quality cost, if any, is a number rather than an impression.
- **Optional oracle:** the same set through Muse Spark (Standard mode, consented demo subset only) to size the local-vs-cloud gap. This informs whether to invest in better prompting/quantization; it never ships, and any quoted gap must name the oracle and the subset.
- **Decision:** the extractor is whichever local model clears the abstention-weighted bar set from E0's confusion costs — possibly split (PLM for the high-volume document pass, Glimmer for hard/reasoning cases). If all fall short, the levers are local — schema/prompt revision, higher-fidelity quantization, embedding-based routing of hard photos to longer Glimmer reasoning, Llama 4 Scout as a last local comparator — not a cloud fallback.

### E4 — Segmentation/cropping ablation: does local SAM 3.1 help extraction?

- **Question:** does extracting from a SAM 3.1 mask/crop (prompt: "sign", "receipt", "menu", "dish") beat whole-image extraction and cheaper local region proposals (Glimmer-proposed boxes, DINOv3/PE dense-feature regions)? SAM 3.1 runs locally from the open checkpoints (848M, CUDA) — no API call involved. Prerequisite: the gated checkpoint access request is a lead action; until granted, run the ablation with the heuristic/embedding crops and SAM 2 (Apache 2.0) as stand-in, and re-run with SAM 3.1 when access lands.
- **Inference path (decided 2026-10-28; lead's gated access to `facebook/sam3.1` is granted and zbook's HF login is active):** no quantization — none is officially published for SAM 3/3.1, the model is small (848M, ~1.7 GB at bf16) next to Glimmer's 17 GB, and mask quality is the variable E4 is measuring, so degrading it to save memory we don't need would confound the ablation. Use **bf16** (the official default) on zbook's base env (torch 2.13.0+rocm10.0.0 TheRock build, transformers 5.15.0, both already installed; `Sam3Model`/`Sam3Processor` present). The real speed lever for our workload is **encode-once, many-prompts**: run the vision encoder once per photo and reuse its features for all prompt phrases ("sign", "receipt", "menu", "dish"), so per-photo cost is one encoder pass plus cheap decoder reads; add `torch.compile` on the encoder only if batch runs make its warmup pay off, and batch images modestly (unified memory is plentiful). Community INT8/FP8, ONNX, and TensorRT routes are CUDA-centric and unproven on ROCm/gfx1151 — revisit only if measured bf16 throughput actually hurts. Expectation to verify in the probe: an encoder pass on the 8060S should cost well under the ~47 s full-res Glimmer prefill it precedes, in which case segmentation latency is not the deciding factor for E4 anyway.
- **Metrics:** same extraction metrics as E3, per condition; mask failure modes on cluttered restaurant photos; SAM runtime/VRAM on the PRO 6000 and (stretch) Strix Halo.
- **Pass/kill:** adopt segmentation only if it measurably improves extraction over whole-image and over the best cheap crop; otherwise it stays out (segmentation is not identification, and adding it for its own sake is model-count padding).

### E5 — Visit reconstruction with local Glimmer (+ deterministic grouping)

- **Question:** given a photo cluster + check-in/location records with known conflicts, can local Glimmer (reasoning over DINOv3/metadata-proposed groupings) reconstruct visits — and state uncertainty — well enough to ship?
- **Tests:** clusters proposed by time/GPS/DINOv3 similarity, reconciled by Glimmer with a structured-output schema: proposed visits, evidence links per claim, confidence, explicit unknowns, and a targeted follow-up question when evidence is missing. Compare two conditions: Glimmer alone on raw clusters vs. Glimmer over deterministic pre-grouping. An optional Spark/Wonder oracle run (consented subset, disclosed) sizes the remaining gap on the hardest clusters.
- **Metrics:** visit-grouping precision/recall against E0 labels; place-resolution accuracy; evidence-link correctness; conflict handling (nearby observation never upgraded to confirmed visit); targeted-question usefulness (would the answer actually decide the case?).
- **Decision:** confirms the reconstruction design and whether the agentic "ask one good question" loop is real or cut. There is no cloud engine to fall back to; a shortfall is fixed with better grouping, schema, or confirmation UX.

### E6 — Agentic geospatial retrieval and taste profile

- **Question:** can an agent (winner of E5, tool-calling over the local index) answer the E0 golden queries — vague-memory, near-a-place, what-was-good-last-time — by planning lookups (geospatial filter → visit → dishes/orders → evidence) instead of plain vector search?
- **Metrics:** golden-query success rate vs. a plain embedding-search baseline (this comparison is what keeps us out of "basic RAG" territory); answer evidence shown for every claim; correct "you haven't been / unknown" answers.
- **Taste profile test:** build the profile only from factual signals — recurrence counts by dish/cuisine/place, repeat visits, user-confirmed likes — then test it predicts held-out repeat visits/orders better than a most-frequent baseline. **Guardrails:** frequency in photos is biased (photogenic food, trips vs. daily life, photographing the special not the usual); the profile must show its evidence and accept corrections. It is a food/place preference summary, never a personality analysis (personality analyzers are an anti-project).

### E7 — Stretch probes (only after E1–E6)

- **Voice (remove the exception if possible):** probe local ASR first — SeamlessM4T v2 (and MMS if a lighter model is needed) on spoken recollections in the demo languages, measuring word error rate and the Japanese case specifically; note the CC BY-NC 4.0 license in the decision. Only if local ASR is unusable, evaluate Muse Voice Transcribe under the exception rules (off by default, audio only, labeled; verify its evaluated-language list covers Japanese). If neither is acceptable, cut voice. Never route image or location data through this path.
- **Muse Image:** none for the core; revisit only for clearly-labeled presentation material after the submission's main claims are true.

## 6. What would change our mind

- E3 shows local Glimmer extraction is not good enough even after prompt/schema and quantization levers → narrow the product's claims (e.g. extraction becomes draft-plus-user-confirmation everywhere, automated resolution only above a measured confidence bar). Reopening cloud processing would require a new lead decision superseding the local-only decision above; it is not a silent fallback.
- E2 shows Strix Halo multimodal Glimmer is impractical → the consumer-hardware story becomes DINOv3 classification/embedding locally with Glimmer requiring a discrete GPU; state the hardware floor honestly in PLAN.md and the demo. *(Partially retired 2026-10-28: Strix Halo vision works (§3); what remains of this risk is throughput at full resolution, which the downscale measurement will either close or price into the hardware-floor statement.)*
- E1's head beats Glimmer on triage accuracy → prefer the head for routing (cheaper, deterministic), Glimmer for extraction only.
- E5 shows models confidently resolving visits that the evidence cannot decide → reconstruction becomes suggestion-plus-confirmation by default; automated resolution only above a measured confidence bar.
- Golden queries (E6) don't beat plain search → the agent layer is unjustified; ship the evidence-linked index and direct filters instead, and drop the agentic-bonus claim.
