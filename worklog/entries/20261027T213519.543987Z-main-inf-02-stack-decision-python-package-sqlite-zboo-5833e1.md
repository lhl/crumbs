# INF-02 stack decision: Python package, SQLite, zbook processing

## Summary

INF-02 decided, and PLAN §5's *(verify)* marks resolved accordingly in the punchlist note below. (1) **Backend/pipeline: a single Python package (`crumbs/`) with a CLI of explicit stages** (import → embed → group → classify → export) rather than a service framework first: the pipeline stages are the product risk, the API (PLAN §API) becomes a thin layer over the same SQLite store once the stages produce real data. (2) **Store: SQLite** (stdlib, WAL) with PLAN §6's provenance discipline enforced structurally — source rows are `observed` and immutable, derived rows are append-only and versioned by `model`/`checkpoint`/`created_by`. Vector storage is float32 BLOBs in the embeddings table; at corpus scale (10^5) a sqlite-vec/FAISS index is a later optimization, brute-force cosine in numpy is fine and honest. (3) **Processing host: zbook** (Radeon 8060S) is the reference box until further notice, per the lead's 'skip PRO 6000' call — Glimmer via llama-server (OpenAI-compatible, localhost), DINOv3/SAM via transformers on ROCm torch; the PRO 6000/vLLM/SGLang arm is deferred, not cancelled (GLM-01/02 stay open). (4) **Frontend:** the PWA grows out of `spike/map-globe/` (MapLibre + local PMTiles already proven); a framework choice is deferred until real visit data drives the flows. (5) **Jobs:** stages are idempotent CLI runs over the store (content-hash dedupe, per-item rows) — no queue infrastructure until background/incremental import (IMP-05) needs it. Job-queue, FastAPI, and sqlite-vec are the named revisit points, triggered by API-01 and 10x scale respectively. **Timestamps caveat:** EXIF times are stored as local camera time with an explicit `captured_at_source`; timezone inference (IMP-03) is still owed and grouping treats times as camera-local within a trip until then.
