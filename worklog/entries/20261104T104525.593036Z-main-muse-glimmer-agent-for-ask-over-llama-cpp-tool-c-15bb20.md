# Muse Glimmer agent for Ask over llama.cpp tool calls

## Summary

Ask can now run as a Muse Glimmer agent. Glimmer plans tool calls over the local index and writes a 1–3 sentence answer that cites visits; the evidence cards come only from tool results. It runs on the existing self-hosted zbook Q4_K_M `llama-server` (`--jinja`, 1 slot, 8k context, DFlash draft), where llama.cpp parses Glimmer tool calls natively. Live run on 8 real questions: Glimmer answered all 8, with 0 unsupported citations, median 21.5 s and max 33 s. The deterministic parser stays as the tool layer and the fallback.

## Changes

- `crumbs/agent.py`: tools are `search_dishes`, `food_visits_in_city`, `visits_at_place` (place registry first, then names read in photos, labelled unverified), `visit_details`, and `visits_near_me` (offered only when a location is given). Glimmer receives compact text results only, never photos or coordinates. Up to 3 tool rounds, then a forced answer. One retry on HTTP errors, and a re-ask for text when the answer comes back empty. Citations of visits no tool returned are stripped and reported. With no tool results the status is unknown. If Glimmer is unreachable before any tool result, the parser answers and the response says so.
- System prompt rules: everything mentioned must come from tool results; candidate places are hedged; photo-text names are reported as "photo text reads X", not as verified places; never infer a restaurant from food appearance; unknown is a valid answer. The city tool says its name list is a lookup list, not where the user has been; an earlier wording led Glimmer to state otherwise.
- `crumbs/ask.py`: extracted `place_visit_cards` and `food_visit_cards` so the parser and the agent share them; "ever", "never" and "any" are now stopwords.
- Wiring: `crumbs ask --agent` prints the answer, cards and tool trace; `GET /v1/ask?agent=1`; the PWA Ask panel has a "Muse Glimmer agent" toggle (on by default) and a collapsible trace showing tool(args) → found and the latency.
- Docs: MODELS.md (Glimmer role, agent measurements, llama.cpp vs. vLLM parser note), DEMO.md (beat 3 agent mode, pipeline row 9), IMPLEMENTATION.md AGT-02 note.

## Validation

- Tool-call probe on the zbook server with a synthetic tool and synthetic question: it returned a parsed `tool_calls` entry with schema-valid arguments, empty `content`, and reasoning in `reasoning_content`; 6.8 s, ~25 tok/s.
- `python3 -m unittest discover -s tests`: 34 passed. New `tests/test_agent.py` (8 tests, scripted fake model over the synthetic store) covers the tool-then-cited-answer flow, removal of invented citations, no-results → unknown, the city-lookup error reaching the model, the place → photo-text lookup, retry after a 500 and an empty answer, the parser fallback when offline, and cards surviving a mid-loop failure. The synthetic fixture moved into `build_store()` so both test files share it.
- Live, through an SSH tunnel to zbook's loopback-bound server on the real store (8 questions covering dish, city, city+year, place-less dish, never-visited city, and absent dish in a city): 8/8 agent-answered, 0 unsupported citations, 0–2 tool calls each, latencies 11.3–32.9 s. Two intermittent faults (a llama.cpp 500 on a later round, an empty final answer) were seen once each before the retry/re-ask handling was added, and did not recur on reruns. No golden-query accuracy is claimed.
- Surface check: API on a scratch DB copy plus Vite dev in headless Chromium with the agent toggle on rendered the answer, the trace ("1 lookup · 18.6s", `search_dishes(soup dumpling, taipei) → 1 found`), a card and 4 thumbnails, with no console errors. Servers were stopped afterwards; screenshots stay outside the repo.
- Privacy: tool-result text (dates, dish and place names) goes to the owner's own zbook over SSH. Nothing goes to a third-party API.
