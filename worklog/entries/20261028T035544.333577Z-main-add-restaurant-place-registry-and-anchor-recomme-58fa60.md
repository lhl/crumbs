# Add restaurant place registry and anchor-recommendation use case

## Summary

Lead-directed addition, now in PLAN §4 (use case 8), §6 (`PlaceCandidate`), §7 stage 5, and IMPLEMENTATION REC-07: restaurants and other venues must exist as a **searchable place registry**, not just per-photo inferences, so the anchor-recommendation flow works — the user names one famous anchor (their example: the Noma popup in Kyoto), a neighborhood, and a rough time, and Crumbs finds the *other* places from that trip (the dashi restaurant, the tempura place) out of photos + geo + time. Design rules recorded with it: candidate places for a visit are **triangulated** from ranked evidence (check-in match > place-name text read from the visit's own photos matched against nearby named places > GPS proximity shown with distance; dish appearance is never identity, per PLAN principle 3); nothing is auto-confirmed on GPS alone; unresolvable visits stay 'unnamed place near <area>' with candidates listed. Place data is OSM-derived and locally cached (PMTiles POI layers keep demo regions offline; Overpass/provider lookups populate the cache elsewhere and are `lookup` provenance, disclosed — the lookup learns an area, never a photo). The registry is queryable by name, anchor place, radius, kind/cuisine, and time window, which is the substrate AGT-01's tools and the share-shortlist (AGT-08) will consume.

## Changes

- `PLAN.md`: use case 8 (recommend from an anchor place, with the triangulation ranking), `PlaceCandidate` row in the data model, stage-5 triangulation paragraph.

Implementation follows in the next unit (schema + lookup + search CLI, run over food-bearing visits).
