# Decision Index 0.3 and JevBench for the no-training Glimmer readout

## Summary

The Decision Index 0.3 public suite ran end to end against Muse Glimmer 30B on
four independent vLLM replicas (FP8, one GPU each, 8,192-token context), read
through a no-training restricted letter readout: **Decision Index 32.60**
(`balanced_skill`; `balanced_raw` 47.40, `breadth_skill` 31.26). Of 140,178
scoreable rows, 125,675 answered (89.65%), 14,503 were recorded unsupported
(10.35%), 0 errored and 0 were left pending; 300,718 of 323,259 questions were
answered. Almost all coverage loss is structural: 14,500 rows ask questions with
more than 26 options (BANKING77, CLINC150+OOS, API-Bank, POP909-CL and 3,412 of
ChessBench's 5,000 rows) and 313 rows exceed the served 8,192-token context and
were refused rather than truncated.

JevBench, recomputed from the stored outputs rather than from the run logs, is
177/231 = 76.62% ± 2.78 pp (one raw read) and 171/231 = 74.03% ± 2.89 pp (cyclic
rotations averaged in log space, without AnyJev's batch prior division), with
zero error rows and every item scored.

Nothing here is a trained decision engine, a calibrated readout, or a board
submission. It is an inference technique over stock weights, and the scores are
not comparable to Decision Index leaderboard entries: different readout, an
8,192-token cap, unsupported rows counted as wrong by the coverage adjustment,
no official latency protocol, and GPUs shared with the extraction job.

## Validation

### Readout, fixed for every question

State (compact JSON when not a string), then the question's instructions, then
the lettered options (`A. <label> - <criterion>`), then "Respond with only the
uppercase letter." The assistant turn is prefilled with "Answer:"
(`continue_final_message`, `add_generation_prompt: false`), `max_tokens: 1`,
temperature 0. The next-token logprobs over the 26 letter token ids
(`logprob_token_ids`, so no letter falls outside a top-k window) are normalised
over the offered options and the argmax is the answer. `noul` questions are
offered `A. Yes / B. No` and answer `P(yes) = P(A) / (P(A) + P(B))`. No
training, no adapter, no calibration, no per-benchmark prompt change, no retry
on a wrong answer, no truncation. A read whose offered-option mass is below
1e-6 is recorded unsupported rather than given a default answer.

```bash
# suite load + run (two segments: first pass, then the corrected noul resume)
PYTHONPATH=~/decision-index python3 /tmp/di_glimmer_run.py \
  --out /tmp/di-0.3-glimmer --workers 40
# scoring with the kit's own scorer
PYTHONPATH=. python3 -m decision_index score \
  --results /tmp/di-0.3-glimmer/results.jsonl \
  --suite-dir /data/decision-index-de2-suite/suite-0.3 \
  --engine glimmer-restricted-letter-readout
```

### Limitations

- Not comparable to the Decision Index board: no submission, no official
  latency measurement, a restricted 26-letter readout, an 8,192-token served
  context, and 10.35% of scoreable rows unsupported (counted as wrong by the
  coverage adjustment).
- The 26-option cap makes five benchmarks unusable and truncates ChessBench to
  its small-option rows; the context cap costs 313 rows. Both are structural
  for this serving configuration, not random sampling.
- One read per question: no cyclic rotations or label-prior correction for the
  Decision Index run. The JevBench rotation arm averages rotations in log space
  without AnyJev's batch prior division, so it is not full L0.
- vLLM FP8 serving is not deterministic under batching; identical prompts can
  differ in the low decimals, and the kit's own notes report 85-98% agreement
  across vLLM reruns. No rerun-to-agree was performed.
- JevBench's 231 items are a separate public suite with mixed tier versions
  (v1.1 easy, v1.2 hard); they are not part of Decision Index 0.3 and its
  numbers do not map onto the index.
- The 6-dp rounding artifact above affects only the stored distribution's
  argmax, not the recorded answer.
- GPUs were shared with the selective-extraction job during the run, so the
  latency figures describe contention, not the model.
