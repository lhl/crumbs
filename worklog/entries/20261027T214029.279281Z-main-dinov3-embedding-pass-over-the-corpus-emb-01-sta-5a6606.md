# DINOv3 embedding pass over the corpus (EMB-01 start)

## Summary

All 440 corpus photos are embedded with DINOv3 ViT-L/16 (camenduru mirror weights; official gate still pending) and vectors live in the evidence store: `crumbs embed` ran on zbook in 21.5 s end-to-end (20.5 img/s through the Python pipeline — PIL load + processor + batching — vs ~200 img/s in the bare forward-pass microbenchmark; the gap is I/O and preprocessing, recorded so nobody quotes the wrong number). Similarity scan note: the cosine baseline for DINOv3 CLS embeddings is high, so naive thresholds mislead — 78 pairs ≥0.90, 6 pairs ≥0.95 (the plausible burst/near-duplicate set), 0 at ≥0.98. EMB-04's pair labels must set the real threshold; the 0.95 candidate list is the labeling starting point. Embeddings are stored per model string, so PE vectors (EMB-02) will coexist for the E1 bake-off.

## Changes

- `crumbs/embed.py`: `embed_all` (transformers DINOv3 over analysis JPEGs, batched, skips already-embedded, float32 BLOB storage) and `similarity_report` (cosine pairs above a threshold).
- `crumbs/cli.py`: `embed` and `similar` subcommands. Processing ran on zbook against a synced copy of `data/crumbs/`; the updated database was synced back (embeddings are derived rows; the local DB remains the working store, all under ignored `data/`).

## Validation

- `embed`: `{'embedded': 440, 'seconds': 21.5, 'img_per_s': 20.5}`; `similar --threshold 0.98` returns 440 vectors, 0 pairs (expected given the measured cosine baseline).
- Threshold sweep computed from the stored vectors: ≥0.90 → 78 pairs, ≥0.95 → 6, ≥0.99 → 0.
