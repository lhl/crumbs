# Generative Glimmer full run on 4 PRO 6000 replicas

## Summary

The full generative Glimmer classification (the `crumbs/classify.py` prompt and schema, unchanged) ran over all 9,669 corpus photos on the dev box: four vLLM replicas of the FP8 checkpoint, one per PRO 6000, sharded file lists, 16 client workers each. Total wall was about 12 minutes (~13 photos/s aggregate, ~0.30 s/photo per replica) against 19.4 s/photo for the same read on the zbook llama.cpp server — with the caveat that the zbook figure is single-slot sequential and the dev figure is concurrent, so the honest per-stream comparison is the pilot's 0.26 s/photo at c=16 on one replica. On the 440 labeled photos the dev generative run agrees with the zbook generative run on 79.3% of categories and scores food F1 0.930 (recall 0.984, precision 0.882) against the zbook run's 0.976 (precision 0.968) — same recall, more food false positives, from some mix of FP8 quantization, 640 px previews instead of 1024 px analysis images, and sampling variance; the non-food accuracy comparison (0.789) carries the usual default-confirmed-label bias. One vLLM behaviour is now on record: guided-JSON generations intermittently pad whitespace to the token cap instead of stopping (llama.cpp stops cleanly on the same prompt), so 9,230 of 9,669 outputs were recovered by extracting category/evidence from the JSON prefix — category is unaffected (it is emitted first), evidence lists may be truncated in recovered rows. Extra replicas were pulled down after the run; the GPU0 Glimmer endpoint remains up.
