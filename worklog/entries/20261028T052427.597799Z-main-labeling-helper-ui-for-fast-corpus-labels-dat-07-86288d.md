# Labeling helper UI for fast corpus labels (DAT-07)

## Summary

DAT-07 built: `crumbs label` serves a one-photo-at-a-time review UI on localhost for fast human labeling — the efficient data-collection answer for scoring. Each screen shows the photo, the model's current category/evidence, and the visit's place candidates as suggestions; labeling is one click/keypress to confirm or correct the category (keys 1–5), plus optional free-text dishes and place name. Queue order prioritizes by labeling value: food photos first, then model-unknowns, then the rest. Labels land as append-only rows in the new `labels` table (category/dish/place, source='user'), never overwriting model output, so label history is auditable and scoring joins labels to classifications cleanly. End-to-end smoke-tested against the real corpus (queue served the first food photo with its candidates; a posted label round-tripped into SQLite and was removed after the test). What it is not yet: a scorer — once ~50–100 category labels exist, a `score` command should emit the confusion table (it needs the labels first); batch/burst labeling (same-visit propagate) is the obvious v2 speed lever.

## Changes

- `crumbs/label_server.py`: stdlib HTTP server (no new deps), inline UI (photo, suggestions, category keys, dish/place text, progress), `/api/next` priority queue, `/api/label` append-only writes, `/img/<id>.jpg` analysis-image serving.
- `crumbs/db.py`: `labels` table. `crumbs/cli.py`: `label [--port]` subcommand.

## Validation

- Live smoke: page 200; `/api/next` returned the first queued item (a food photo with 6 place candidates and distances); POST `/api/label` returned ok and the row was verified in SQLite, then deleted to keep the label set clean; server stopped.
