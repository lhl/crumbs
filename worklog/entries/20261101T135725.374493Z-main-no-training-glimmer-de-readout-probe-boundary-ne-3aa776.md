# No-training Glimmer-DE readout probe: boundary needs prefill

## Summary

A no-training Glimmer-DE — Muse Glimmer read DE-style, letter-coded options with the distribution taken from next-token logprobs, no LoRA and no training — is mechanically feasible on the zbook llama.cpp server, with three measured caveats. First, the naive scaffold fails: asked to 'respond with only the letter', Glimmer starts reasoning instead (first token ' to', answer mass 0.000 on 12/12 photos). An assistant prefill ('The category is ') fixes the boundary: answer mass 0.45-0.91 and sensible distributions, 3/4 correct on a 4-photo spot check. Second, a raw read costs ~6.4 s per question — the image prefill (~1,131 tokens) is re-paid per request, so AnyJev-style rotation averaging (5 rotations ≈ 32 s) is currently slower than the generative classification it would replace (19.4 s); one prompt-cache hit (0.4 s for a byte-identical repeat) shows the cache exists but does not engage across option-order changes. Third, readout quality is uneven across rotations: one of five rotations of the same photo collapsed to answer mass 0.002, which is exactly the failure AnyJev's answer-mass diagnostic exists to catch — a mass floor with fallback to the generative read is required, not optional. Review basis: the shisa-de SDK/DE-2.1 readout contract (trained readout; its accuracy does not transfer to an untrained model) and AnyJev (Nokia, Apache-2.0), whose training-free L0 level — cyclic option rotations averaged in log space plus a label-prior division estimated without labels — is the applicable technique; its llama.cpp backend is text-oriented, so the Crumbs readout would be implemented against llama-server directly, as this probe was.

## Changes

- No repo code. Probes run from `/tmp` against the zbook Glimmer server (`glimmer_de_probe.py` 1-3): 12 photos naive scaffold, 4 photos with assistant prefill, 5 rotations of one photo.
- AnyJev and the shisa-de SDK were reviewed from their public repos/model card for this entry; no code copied.

## Validation

- Naive scaffold: 12/12 photos first token ' to', letter mass 0.000 — prompt does not land without the prefill.
- Prefill scaffold: masses 0.910/0.714/0.809/0.450; predictions food/trip/sightseeing correct and one food photo read as trip (0.90) against owner labels; per-read wall 5.5-6.5 s.
- Rotations of one food photo: food probability 0.99-1.00 across rotations 0-3 (stable), rotation 4 mass collapsed to 0.002; timings 0.4 s (cache hit) then 6.4 s per rotation.

## Next

- Accuracy is the open question (n=4 proves mechanics, not quality): run raw category reads over all 440 labeled photos (~47 min of zbook server time) and score against the owner labels next to generative Glimmer (food F1 0.976) and DE-2.1 (0.89-0.90).
- If the read earns a place: implement as a `crumbs` stage with the prefill scaffold, an answer-mass floor with generative fallback, and single (raw) reads by default; adopt AnyJev L0 rotations/prior correction only if prompt caching across rotations is made to engage. Calibration (temperature on the read distribution) can be fitted on the 440 labels without any model training.
