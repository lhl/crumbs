# Fix multi-frame HEIC analysis images in importer

## Summary

The 2025/2026 iCloud import silently produced no analysis image for 4 of 9,669 media items, and the first downstream consumer (DINOv3 embed) crashed on the first of them. Root cause: those HEIC files carry multiple frames (main image plus auxiliary frames), and ImageMagick answers such an input by writing `dest-0.jpg`, `dest-1.jpg`, `dest-2.jpg` with returncode 0 — so the importer's success check passed while the expected `dest.jpg` never existed, and the import's own stats reported `analysis_failed: 0`. The importer now selects frame `[0]` explicitly and treats a missing destination after conversion as a failure. The four affected photos were repaired in place (frame 0 renamed to the canonical analysis name, auxiliary frame files removed); every media item now has exactly one analysis image.

## Changes

- `crumbs/importer.py`: `magick "src[0]"` in `make_analysis_image`, plus a `dest.exists()` check in the failure condition (returncode alone is not sufficient evidence of success).
- Local only (not repo state): repaired `data/crumbs/analysis/` — 4 frame-0 files renamed to `<hash>.jpg`, 8 auxiliary frame files deleted; file count now equals the media count (9,669).

## Validation

- `magick identify` on an affected source shows 3 frames (5712x4284 main + two 2688x2016), reproducing the mechanism.
- After repair: scripted check over the DB reports 0 media missing an analysis image; analysis directory holds exactly 9,669 JPEGs.
- `python3 -m py_compile crumbs/importer.py` passes. DINOv3 embed was restarted against the repaired set.
- Note for result hygiene: the file-glob runners (PE/SAM/Glimmer-DE) processed the 8 auxiliary frame files as extra photos before cleanup; they share no media hash filename, so hash-keyed joins ignore them, but raw row counts from those runs are inflated by up to 8.
