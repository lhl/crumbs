# Repair Glimmer serving contract and extraction resume failures

## Summary

The post-classification pipeline was not complete at the pre-compaction handoff. The extraction process exited zero but reported only 308 successful reads of 3,103 targets and 2,795 failures after its SSH tunnel timed out. The place-fetch/reconcile shell also exited zero despite both stages reporting `sqlite3.OperationalError: database is locked`. Those process exits are not successful stage results. This checkpoint fixes the model-serving contract and transaction lifetime, validates resumability through the CLI, and verifies one real dev FP8 extraction. The remaining corpus extraction and reconciliation still need execution.

## Changes

- `GLIMMER_MODEL` selects the vLLM request dialect and supplies the served model ID; the default retains the llama.cpp schema dialect. Both classify and extract use the same request builder.
- New outputs name the configured model ID as their checkpoint instead of falsely calling FP8 reads GGUF. The existing 375 extraction rows labeled `gguf-q4_k_m+mmproj` include the earlier 308 dev successes; these immutable rows are retained, but that subset's checkpoint label is inaccurate. The new correctly identified FP8 pass will not skip them.
- Classification and extraction commit each successful result before waiting for another model response, rather than holding SQLite's write lock across several network calls.
- Extraction supports `--workers` (default four), bounds queued requests, stops scheduling after a transport/server failure, reports unattempted targets, and exits nonzero on partial failure. Successful rows remain resumable by checkpoint.
- Added six standard-library tests using synthetic database records and a fake HTTP model server. No real images, source paths, transcripts, or inference content are committed.
